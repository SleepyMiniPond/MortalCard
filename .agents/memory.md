# AI 工作記憶

> 最後更新：2026-08-11

## 文件與草稿偏好

- 使用者偏好將「製作中的設計草稿、分析草稿、短期工作筆記」與正式專案文件分離。
- 臨時草稿請放在 `.agents/working/`，不要放進 `Document/`。
- `.agents/working/` 的內容不需要永久留存，也不應納入 git。
- `Document/` 只放正式、值得長期維護的專案文件。
- 若需要讓未來 AI 也知道長期協作偏好，優先更新本檔與 `AGENTS.md`。

## Git 工作偏好

- 不要主動 stage 或 commit 修改，除非使用者明確要求。
- 使用者會一邊檢查 change，一邊自行把看完的內容加入 stage。
- 若發現檔案已 staged，不要自動 unstage；視為使用者已檢查或正在整理。
- 完成工作時只回報變更內容、驗證結果與目前 git 狀態。

## Unity 驗證偏好

- 本專案需要 Unity 驗證、AssetDatabase refresh、編譯檢查或 EditMode/PlayMode 測試時，優先使用 Unity MCP，連到使用者已開啟的 Unity Editor。
- 若原生 MCP tool 沒有直接暴露，改用 `unity-mcp-cli run-tool ...` 呼叫 MCP，例如 `unity-mcp-cli run-tool tests-run --input-file <json>`。
- 不要優先使用 Unity `-batchmode` 開第二個 Editor；本專案常態會有 Unity Editor 開著，batchmode 容易被 project lock 擋住。
- 只有在 MCP 不可用、使用者明確同意、或需要驗證 MCP 本身不可用時，才把 batchmode 當 fallback，且必須清楚回報原因。

## Runtime 與 Validator 程式風格

- Runtime 只處理遊戲機制中合理可能發生的失效，例如排隊中的後續 Effect 因前一個 Effect 已移除目標而找不到 Buff；這類情況應安靜 No-op／Rejected。
- Library、CardData、必要 ID、Operation、Condition 等企劃資產缺失，應由 Validator 在執行前排除；Runtime 核心邏輯不要重複堆疊 null 或缺少資料的防禦判斷。
- 若檢查源自同一語意有兩份輸入，優先改為單一資料來源，讓 Script 直接呈現遊戲流程。
- 玩家輸入、存檔與網路資料等未經專案 Validator 保證的外部邊界，仍需正常驗證。

## 大型跨層任務的協作經驗（T-010 復盤）

> 這一節來自 T-010 卡片變身系統的單次合作經驗，屬於可調整的參考原則，不是強制工作流程。主要適用於歷時數天、橫跨 Data／Model／Presenter／View／持久化等多層的大型任務；小型修正、明確重構或仍在探索的需求，不必為了遵循本節而增加文件或決策負擔。

### 規格與決策

- 大型任務開始實作前，優先找出少數「一旦改變就會造成跨層返工」的決策，例如狀態優先順序、重複套用規則、Clone 語意、勝敗／取消／重試的持久化政策，以及 Runtime 與戰鬥外系統的責任邊界。
- 適合用具體遊戲情境或簡短結果矩陣確認這些決策；不需要把所有細節一次凍結。需求探索期間應明確區分「已確認」、「暫定」與「延後決定」。
- 規格變更是正常現象。若大型任務跨越多個對話，宜維護單一決策紀錄，寫清楚舊決策、新決策與受影響範圍，並同步清理過時描述，避免多份文件各自保留不同版本。
- 只有真正會明顯改變資料結構、玩家行為或持久化結果的選項才需要停下詢問；可逆、局部且符合既有規範的實作細節可直接採合理預設，避免把合作流程變成過度審批。

### 階段與 Review

- 大型任務可拆成可獨立驗證的階段，但應持續區分「本輪完成」、「目前階段完成」與「整個任務完成」，避免階段編號與任務狀態混淆。
- 每次交付優先提供精簡的 review package：本輪改變的行為、驗證結果、仍未完成的範圍、需要使用者決定的事項，以及下一步。詳細實作說明只在有助於判斷時展開。
- 使用者偏好逐步檢查 change 並自行 stage／commit；大型任務繼續保留這種 review gate。若使用者已明確授權連續完成一批工作，則不需要在每個微小內部步驟停下。
- 對相鄰工作標示其性質：核心功能、必要前置重構、順帶發現但延後的問題。大型但可獨立的延伸需求應考慮拆成新的 T 編號，不讓原任務無限擴張。

### 測試與驗收

- 測試的目標是保護重要行為與已發生的 Bug，不是每次修改都機械式增加新測試。既有測試已涵蓋的重構應優先沿用，階段結束時可檢查 Characterization、Baseline、Pipeline 與 Integration 測試是否重複。
- 日常迭代先跑受影響的定向測試；完成一個階段或準備整合時再跑完整 EditMode。若完整測試本身很快，可依當下風險提高執行頻率，不必僵化限制。
- 最終收尾應對照規格、實作、測試與正式文件，並誠實區分自動化覆蓋、人工 smoke test、非阻塞已知邊界，以及明確排除於任務外的工作。

### 使用原則

- 優先保留 T-010 中有效的做法：以遊戲情境討論、逐階段 review、文件與草稿分層、Unity 編譯與回歸驗證、以及不擅自 stage／commit。
- 不應因 T-010 曾出現規格返工，就要求未來所有任務先寫完整規格或決策矩陣。流程的詳細程度應與任務規模、可逆性、跨層影響及需求不確定性成比例。
